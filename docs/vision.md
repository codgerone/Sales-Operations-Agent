# 项目定位与目标

最后更新：2026-11-24（V0 基础搭建）

本文写项目要做成什么、为什么这样做、遵循哪些原则，是规划各版本的依据。它不描述已实现的系统（已实现的写在 `overview.md`、`design.md`）。目标、范围或原则改变时更新本文，并在 `decisions/` 记录原因。

## 1. 一句话

面向海外销售运营的项目管理 Agent：把合同、订单等业务文件变成可核验的业务事实，按事实生成并维护每个项目的执行计划，到期提醒、主动跟进，并能就项目事实与业务知识回答问题。

## 2. 用户与问题

- **用户**：一名海外销售运营人员（单用户），同时跟进十余个项目。
- **项目生命周期**：合同 → 订单 → 生产 → 出货 → 开票 → 回款。
- **痛点**：事实散落在合同、订单、发票、装箱单、进度表与沟通记录中；跨文件整理靠人工，容易重复录入、版本冲突、来源无法追溯；回款、排产、订舱、报关等节点靠人盯，容易遗漏。

## 3. 能力目标

三个层次：**看懂业务**（文件 → 可核验的结构化事实）、**管理业务**（项目全貌、计划、待办与风险）、**推动业务**（在权限与审批约束下准备并执行跟进动作）。

| 用户功能 | 内容 | 主要技术 |
|---|---|---|
| 项目导入与补充 | 上传文件 → 解析、提取、核对 → 拟变更集 → 用户审批 → 写入业务数据库；导入新项目与补充已有项目共用同一流程，在目标识别、查重、更新策略上分支 | 文档解析（复用 Minimal-RAG）、LLM 结构化提取、受控 Workflow、人工审批 |
| 项目概览 | 业务事实视图（客户、合同、订单、金额、交付、回款）与执行计划视图（任务、依赖、计划与实际日期、阻塞、风险） | 业务数据库、查询 API、前端 |
| 待办提醒 | 即将到期、已逾期、被阻塞、等待回复超时的事项 | 计划引擎、后台调度 |
| 行动跟进 | 准备沟通内容、经审批发送、理解回复、核验后更新状态、识别偏差并升级、提出可验证的备选方案供用户决策 | Agent、工具调用、审批、模拟的外部各方 |
| 问答 | 项目事实走数据库精确查询，文件与业务知识走 RAG，一个问题可同时用到两者，回答带来源 | 工具调用、路由、Minimal-RAG |

## 4. 后台能力模块

用户功能是使用入口，后台按能力模块搭建，二者不一一对应。模块是同一后端项目中的代码模块（模块化单体），不是独立部署的服务，也不是各自一个 Agent。模块之间通过明确的函数接口、业务事件或受控命令协作，不直接改写其他模块管理的数据。

| 模块 | 职责 | 服务的用户功能 | 搭建阶段 |
|---|---|---|---|
| 业务数据 | 客户、合同、订单、交付、付款等业务事实的模型、存储、读写接口；事务、并发控制、审计 | 全部（事实的唯一来源） | 1 |
| LLM 调用层 | 所有 LLM 调用的统一入口：结构化输出与校验、超时重试与降级、模型路由、限流、缓存、调用记录与成本 | 导入、问答、跟进 | 2 |
| 文档处理 | 文件解析（复用 Minimal-RAG）、业务文档分类、结构化提取、来源证据 | 导入与补充 | 3 |
| 导入与变更管理 | 校验与标准化、实体匹配、字段比较、拟变更集、导入流程、人工审批、幂等的事务写入 | 导入与补充；跟进中产生的事实更新 | 4 |
| 计划引擎 | 由业务事实与流程模板生成项目执行计划（任务、里程碑、依赖、日期规则）；日期计算、阻塞判断、影响分析与重算、计划版本 | 概览（计划视图）、提醒、跟进 | 5 |
| 事件与后台任务 | 业务事件的记录与消费、后台 Worker、定时扫描、提醒 | 提醒；连接导入 → 计划、事实变更 → 重算 | 6 |
| Agent 运行时 | 工具调用循环、工具注册与权限、步数熔断、上下文管理、会话与长期记忆、Skills、子 Agent、调用轨迹 | 问答、跟进 | 7（记忆、Skills、子 Agent 在 9） |
| 知识检索 | 接入 Minimal-RAG 检索（候选：MCP Server） | 问答、跟进 | 7 |
| 问答 | 问答 Agent：事实查询与知识检索的路由与组合、引用 | 问答 | 8 |
| 跟进与协调 | 跟进任务执行、模拟外部各方、跟进 Agent、异常协调与再规划 | 行动跟进、提醒 | 9 |
| 评测与可观测性 | 评测集与评测页（各模块各自建）、跨模块调用轨迹与成本统计、整体 Agent 评测 | 横向 | 各阶段；整体在 10 |
| 接口与前端 | REST API（各模块随阶段提供）、用户界面 | 全部 | API 随阶段；界面在 10 |

调用关系：一次导入依次经过文档处理 → 导入与变更管理 → 业务数据，写入成功产生事件，由事件与后台任务触发计划引擎生成计划；计划的生成与重算只在计划引擎中实现，不因入口不同而复制。

## 5. 产品与业务原则

1. **业务事实只有一个权威来源：业务数据库。** LLM 输出、Workflow 状态与检查点、Agent 记忆都不是事实；数据库回答"业务现在是什么状态"，Workflow 状态只回答"这一次程序执行到哪里"。
2. **流程固定的部分用 Workflow 与确定性代码**，只把需要理解、提取、动态决策的环节交给 LLM 或 Agent。每一处用不用 LLM，都要说得出理由。
3. **写入业务事实与对外动作都经后端校验和用户审批。** 权限、放行条件等硬约束由代码执行，不靠提示词；Agent 可以提议，不能绕过。
4. **文件内容与外部回复是不可信数据**，其中的指令性文字不改变系统行为。
5. **可溯源、可审计**：每个事实能追到来源文件与文件内位置；每次变更记录依据、审批与操作者。
6. **业务依赖图与程序执行图分开**：项目的任务依赖是业务数据，存在数据库；Workflow 图是程序逻辑，一套 Workflow 服务所有项目。
7. **四种时间分开**：合同约束（规则）、预测日期、实际日期、据实际事件确定的正式到期日。未知的日期保持未知，不臆造；内部计划延期不等于合同交期延期。
8. **三类状态分开**：跟进任务状态（已联系、等待回复…）、业务任务状态（进行中、阻塞…）、业务事实及其核验状态（款项是否实际到账）。发送成功不等于业务完成；"应该能按时完成"是声明，不是事实。
9. **先有业务需要，再选技术**；技术名词不是目标。多 Agent、MCP、长期记忆等只在有明确使用场景时引入。
10. **结论来自评测**：提取、匹配、提醒、Agent 行为都要有标注数据与指标，效果以实测为准，不预先承诺。

## 6. 简历展示目标

项目要让面试官看到一条完整的闭环：**输入 → 判断 → 审核 → 执行 → 可追溯的结果**，并能回答"为什么这里用 Workflow 不用 Agent""为什么要拟变更集和版本检查""工具失败、流程中断、提交成功但响应丢失时怎么办""为什么不默认多 Agent""改动的效果怎么证明"。

| 能力 | 计划中的落点 |
|---|---|
| RAG | 问答中的文件与业务知识检索；解析能力用于导入（Minimal-RAG） |
| Tool / Function calling | 问答 Agent 的项目查询与知识检索工具；跟进 Agent 的起草、发送、记录、提议工具 |
| MCP | 候选：把 Minimal-RAG 的检索包装成 MCP Server，供本项目与其他客户端调用；在接入的版本确认 |
| Skills | 候选：按任务类型（生产跟进、出运、回款）的跟进策略作为按需加载的 Skill |
| Memory | 会话指代（短期）；经授权持久化的用户偏好（长期）；明确不替代业务事实 |
| 子 Agent | 候选：异常协调中由独立上下文的子 Agent 收集与汇总信息；在有实际需要时引入 |
| Workflow / State / Checkpoint / HITL | 导入流程的状态、审批中断与恢复 |
| Guardrails | Schema 与业务规则校验、动作白名单、审批、提示注入防护 |
| 评测与可观测性 | 提取字段级指标、匹配与冲突检测指标、Agent 任务成功率、调用轨迹、延迟与成本 |
| 后端 | 关系建模、REST API、事务、幂等、并发控制、审计、后台任务、事件与 Outbox、部署 |

与 Minimal-RAG 的分工：Minimal-RAG 展示文档解析、检索与检索评测的深度；本项目展示业务驱动的 Agent 与 Workflow 设计、可靠的业务执行闭环与后端能力，不重做 RAG 核心。

## 7. 范围

**完成时包含**：第 3 节的五个用户功能与第 4 节的全部模块。导入支持合同、订单等几类业务文件的单文件导入；跟进与协调覆盖生产、出运、回款三类任务与三个异常场景；有整体评测、可观测性、界面与云端部署。项目全部完成后再用于求职。

**不做（除非之后另行决定）**：多用户与角色权限；真实邮箱、ERP、财务系统接入（先用模拟对象）；工业级排产与跨项目产能优化；微服务与消息中间件；多文件跨文档的自动整合。

## 8. 与 Minimal-RAG 的关系

- **复用**：文档解析（数字 PDF、扫描 PDF、Word、Excel；带文件内地址，可直接作为提取字段的来源证据）与知识库检索。
- **方式在首次接入的版本中确定**：作为库安装、进程内调用，或作为独立服务（MCP / HTTP）调用。约束：Minimal-RAG 依赖重（Docling、PyTorch、约 2.3 GB 的 bge-m3），要求 Python 3.11。
- RAG 本身的改进回到 Minimal-RAG 仓库完成，本项目只通过它的公开接口使用。

## 9. 数据与隐私

- 不使用前雇主的真实文件与商业信息。测试与演示用虚构但符合真实业务习惯的文件，由用户依据工作经验编写，文件与标注都可以公开。
- 外部各方（客户、工厂、财务、货代）在演示中由模拟对象扮演，界面与文档中标明是模拟。
