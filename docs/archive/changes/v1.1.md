## 实施结果与差异

实施于 2026-11-25，七步各一个提交；`uv run pytest` 16 项通过，Ruff 检查与格式检查无问题。

锁定版本：SQLAlchemy 2.1.9、Alembic 1.20.1、psycopg 3.3.9、pydantic-settings 2.16.3、pytest 9.2.0、Ruff 0.17.6；PostgreSQL 18.7（`postgres:18`）。

与提案的差异（都不改变 Q1–Q6 的结论）：

1. **数据库地址的主机用 `127.0.0.1`，不用 `localhost`**。本机 `localhost` 先解析为 IPv6 `::1`，连接挂起直到超时（对照：同一地址只换主机名，`127.0.0.1` 用 0.03 秒连上，`localhost` 在 10 秒超时后才回落到 IPv4）。同时给 Engine 加了 5 秒连接超时，数据库不可达时尽快失败。
2. **数据库停止时，驱动报的原因是 `connection timeout expired`**，不是"拒绝连接"：Docker Desktop 停止容器后仍占着本机 5432 端口。退出码仍是 2。
3. **`alembic.ini` 只用 ASCII 字符**（注释写英文）：Alembic 按系统区域编码（中文 Windows 为 GBK）读它，写中文会报 `UnicodeDecodeError`。
4. **迁移生成后自动跑 Ruff**（`alembic.ini` 的 post_write_hooks：修正导入顺序 + 格式化），迁移模板改为 3.11 写法，使新迁移直接通过 `ruff check` 与 `ruff format --check`。
5. **`db.py` 多一个 `alembic_config(url)`**：测试与 `sales-ops check` 共用，指向给定的库；`env.py` 优先用调用方传入的地址，否则取 `Settings`。
6. **迁移往返测试的空库每次删除重建**（`DROP DATABASE ... WITH (FORCE)` 后再建），比"清空"更彻底。
7. **测试多两项**：`test_import.py`（步骤 1 的导入冒烟测试，保留）；`test_cli.py` 多一种情况"连不上数据库 → 退出码 2"（连 `127.0.0.1:1`）。

版本检查：

- 数据库结构：新建 `customer` 表，迁移 `20261125_be4f2bce3a48_create_customer.py`（自动生成后人工审核，仅删去自动生成标记注释）；`test_migrations.py` 保证能升能降且与模型一致。
- 提示词与提取 Schema：无。
- 已存数据：无。

验收：2026-11-26 用户按"亲手验收步骤"操作一遍，全部符合预期。

## 需要你拍板的问题

**结论（2026-11-25）：Q1–Q6 全部采纳推荐**：Python 3.11；uv；PostgreSQL；Docker Desktop + Compose；SQLAlchemy 2.0 + Alembic；第一张表 `customer`。

### Q1 Python 版本

- **事实**：本机系统 Python 为 3.13.9；uv 管理的 3.11.15 已安装。Minimal-RAG 限定 `>=3.11,<3.12`。3.11 的安全支持到 2027-10。
- **选项**：A. 3.11；B. 3.12 / 3.13。
- **推荐 A**。以库方式（进程内）接入 Minimal-RAG 时本项目必须是 3.11；以服务方式（MCP / HTTP）接入时版本无关。接入方式在 V3.1 决定，选 3.11 两条路都保留，代价只是用不到 3.12 起的少量新语法。
- **影响**：选 B 等于在 V3.1 之前排除库方式接入。知识稿 3.4、3.7。

### Q2 包管理工具

- **事实**：本机已装 uv 0.10.8，Minimal-RAG 用 uv；没有 Poetry。
- **选项**：A. uv；B. Poetry；C. pip + venv + requirements.txt。
- **推荐 A**。有跨平台锁文件、能固定 Python 版本、速度快；库方式接入时可直接写本地路径或 git 标签依赖 Minimal-RAG，两个项目一套工具。C 没有可靠的锁文件；B 需要另装，且不管 Python 版本。
- **影响**：决定日常命令（`uv sync`、`uv run`、`uv add`）。知识稿 3.5、3.6。

### Q3 数据库

- **选项**：A. PostgreSQL；B. SQLite；C. MySQL。
- **推荐 A**。本项目要存金额（定点小数）和跨时区的时刻，有并发修改（V1.4）与后台 Worker（V6.1），迁移失败要能整体回滚。SQLite 没有原生定点小数、只能单写者；MySQL 能用，但 DDL 不在事务里、没有 `timestamptz`。开发、测试、部署用同一种数据库。
- **影响**：选 B 会让 V1.4 的并发演示和 V6.1 的 Worker 失真，且日后换库要重写迁移。知识稿 5.3。与 Minimal-RAG 无关（它的索引在自己的 Chroma 与文件中）。

### Q4 本机怎么运行 PostgreSQL（Q3 选 A 时）

- **事实**：本机没有 Docker，没有 WSL，固件虚拟化已开启，没有本机 PostgreSQL。
- **选项**：A. Docker Desktop + Compose；B. PostgreSQL 官方 Windows 安装包，装成系统服务。
- **推荐 A**。数据库版本、端口、账号写在仓库的 `compose.yaml` 里，一条命令启动、停止、清空重建；系统里不多一个常驻服务；V10.4 部署本来就要用 Docker。代价：安装 Docker Desktop 需要先装 WSL 2（`wsl --install`，需管理员权限，可能要求重启），Docker Desktop 常驻占用内存。
- **影响**：选 A 需要你在实施会话前自己完成安装（见"实施前置"）；选 B 时把 `compose.yaml` 换成一份本机安装与建库说明，其余不变。知识稿 5.4、5.5。

### Q5 ORM 与迁移工具

- **选项**：A. SQLAlchemy 2.0 ORM + Alembic；B. SQLModel + Alembic；C. 原生 SQL + 手写 SQL 迁移文件。
- **推荐 A**。Python 后端的事实标准，对事务、锁、关系控制最细（V1.4、V4.4 用得到）；数据库模型与 API 模型（V1.3）、提取模型（V3.2）分开，符合"提取用的 Schema 与数据库 Schema 可以不同"。B 把表模型和接口模型合成一个类，正好违背这一点，复杂用法仍要回到 SQLAlchemy；C 的模型与迁移两份描述需要人工保持一致。
- **影响**：与 Minimal-RAG 无关；以库方式接入时，依赖兼容性由 uv 在锁定时检查。知识稿 6.4、6.5、7.6。

### Q6 第一张表

- **事实**：V1.1 要跑通"一张表"的全流程；实体与字段的正式设计在 V1.2，由你依据业务决定。
- **选项**：A. `customer`，只有 `id`、`name`（非空）、`created_at` 三列；B. 一张与业务无关的演示表，V1.2 删掉。
- **推荐 A**。客户是最没有争议的实体；V1.2 修改它时会产生第二个迁移，正好演示"在已有表上改结构"。V1.2 可以任意增删它的字段和约束。

### 项目与依赖

- `pyproject.toml`：发行名 `sales-operations-agent`，版本 `1.1.0`，`requires-python = ">=3.11"`；构建后端 hatchling；入口命令 `sales-ops = "sales_ops.cli:main"`。
- `.python-version`：`3.11`。
- `uv.lock` 提交到仓库。
- 运行时依赖：`sqlalchemy`（2.x）、`alembic`、`psycopg[binary]`（3.x）、`pydantic-settings`（2.x）。开发依赖（`dev` 组）：`pytest`、`ruff`。版本范围写"当前大版本内"，确切版本以锁文件为准。
- Ruff：检查与格式化，配置写在 `pyproject.toml`，规则集用默认加 `I`（导入排序）、`UP`（新语法）、`B`（常见错误）。

### 目录

```

  conftest.py
  test_config.py
  test_migrations.py
  test_customer.py
  test_cli.py
```

### 本机数据库（`compose.yaml`）

- 服务 `db`，镜像 `postgres:18`；用户、密码、库名为仅限本机的开发值（用户 `sales_ops`，库 `sales_ops`）；端口只映射到 `127.0.0.1:5432`；命名数据卷持久化数据；健康检查用 `pg_isready`。

### 配置（`config.py`）

- `Settings`（pydantic-settings）：读取环境变量与项目根目录的 `.env`，环境变量优先。
- 字段：`database_url`（必填，`SecretStr`）。V1.1 只有这一项。
- 测试库地址：环境变量 `TEST_DATABASE_URL`；未设置时取 `database_url` 并把库名改为 `<库名>_test`。
- `.env.example` 写本机开发值：`DATABASE_URL=postgresql+psycopg://sales_ops:<开发密码>@localhost:5432/sales_ops`。

### 数据库访问（`db.py`）

- `create_engine_from(url)` 与 `make_session_factory(engine)`：由调用方传入地址创建，模块导入时不连接数据库、不读配置，测试可以指向测试库。
- `Base`：SQLAlchemy 2.0 `DeclarativeBase`，`metadata` 带约束命名约定（主键 `pk_`、外键 `fk_`、唯一 `uq_`、检查 `ck_`、索引 `ix_`）。
- 会话用法：一次操作一个 Session，`with factory() as s, s.begin():`。

### 第一张表（`business/models.py`）

- `Customer` → 表 `customer`：`id` BIGINT IDENTITY 主键；`name` TEXT 非空；`created_at` TIMESTAMPTZ 非空，默认 `now()`（数据库端生成）。

### 迁移

- Alembic 初始化；`env.py` 的数据库地址来自 `Settings`，不写在 `alembic.ini` 里；开启类型比较。
- 第一个迁移：创建 `customer`（自动生成后人工审核）。

### 命令行（`cli.py`）

`sales-ops check` 依次检查并输出，退出码区分失败类型：

| 结果 | 输出 | 退出码 |
|---|---|---|
| 全部正常 | Python 版本、数据库地址（密码遮蔽）、连接正常与服务器版本、迁移版本 = 最新 | 0 |
| 配置缺失或无效 | 缺哪一项、怎么配 | 1 |
| 连不上数据库 | 地址（密码遮蔽）与驱动给出的原因 | 2 |
| 迁移未执行或不是最新 | 当前版本与最新版本 | 3 |

### 测试

- `conftest.py`：
  - 会话级：确定测试库地址；**库名不以 `_test` 结尾则终止**；测试库不存在时创建；连不上数据库时以清楚的消息终止整轮测试（不跳过）；把测试库迁移到最新。
  - 函数级 `session`：每个测试在一个外层事务中运行，Session 以保存点方式加入，测试结束回滚。
- `test_config.py`：缺 `DATABASE_URL` 时报错；环境变量覆盖 `.env`；`SecretStr` 的字符串形式不含密码；测试库地址的推导。
- `test_customer.py`：写入后用新查询读回，`id` 与 `created_at` 由数据库生成；`name` 为空时被数据库拒绝（`IntegrityError`）。
- `test_migrations.py`：在单独的空库 `<库名>_migrations_test`（不存在时创建，测试前清空）上 `upgrade head → downgrade base → upgrade head`；最新迁移与模型一致（Alembic 比较无差异）。
- `test_cli.py`：`check` 在正常、迁移未执行、配置缺失三种情况下的退出码。

### 亲手验收步骤

退出码在 PowerShell 中用 `$LASTEXITCODE` 查看。

| # | 动作与预期 | 目的 |
|---|---|---|
| 1 | `docker compose up -d`，再 `docker compose ps`：`db` 显示 healthy | 确认数据库的版本、账号、端口都由仓库里的 `compose.yaml` 决定，一条命令就能启动；healthy 表示健康检查（`pg_isready`）通过，数据库已能接受连接（Q4） |
| 2 | 复制 `.env.example` 为 `.env` | 确认配置与代码分开：程序连哪个库由 `.env` 决定，代码里不写地址；`.env` 不进 git，`.env.example` 是进 git 的样表 |
| 3 | `uv sync`，再 `uv run python --version`：显示 3.11.x，项目根目录出现 `.venv` | 确认环境能按锁文件原样重建：Python 版本由 `.python-version` 固定为 3.11，依赖版本由 `uv.lock` 固定，装进项目自己的 `.venv`，不影响系统 Python（Q1、Q2） |
| 4 | `uv run sales-ops check`：报告迁移未执行，退出码 3 | 看第一种失败：配置有了、数据库连得上，但表还没建。`check` 能指出问题出在"迁移"这一环，而不是笼统地说"出错了" |
| 5 | `uv run alembic upgrade head`，再 `uv run sales-ops check`：全部正常，退出码 0 | 亲手执行第一个迁移，建出 `customer` 表；数据库记下当前迁移版本，`check` 拿它与迁移链最新版本对比，确认一致（Q5） |
| 6 | `docker compose exec db psql -U sales_ops -c "\d customer"`：看到三列与主键 | 不经过本项目代码，用数据库自带的工具查看迁移建出的真实表结构：三列的类型与非空、`id` 为 identity、主键名 `pk_customer`（命名约定生效）（Q6） |
| 7 | 运行 `uv run python`，粘贴 `overview.md` 第 4 节的代码：写入一个客户、提交、再查询打印；然后 `docker compose exec db psql -U sales_ops -c "select * from customer"` 看到这一行 | 跑通本版目标"模型 → 迁移 → 写入 → 读取"；用 psql 独立核实这一行确实提交进了数据库，而不只是留在 Python 内存里；`id` 与 `created_at` 由数据库生成 |
| 8 | `uv run pytest -v`：看到每个测试的名字与结果；再执行一次第 7 步的 `select`，那一行还在 | 看自动化检查覆盖了什么（配置、读写、约束、迁移、命令行）；测试在单独的测试库里运行并回滚，开发库里你写入的数据不受影响 |
| 9 | `docker compose stop db` 后运行 `uv run sales-ops check`：报告连不上数据库（原因为 `connection timeout expired`，约 5 秒），退出码 2；`docker compose start db` 恢复 | 看第二种失败：连不上数据库与第 4 步的"迁移未执行"给出不同的消息与退出码；有连接超时，不会一直卡住 |
| 10 | `uv run alembic downgrade base`，再运行第 6 步的 `\d customer` 命令：显示 `Did not find any relation named "customer".`；`uv run alembic upgrade head` 恢复 | 确认迁移可逆：每个迁移都有能执行的 `downgrade`。降级会删表，第 7 步写入的那一行随之消失，升级后是一张空表——迁移管的是结构，数据要另行保护 |
