# 路线图

最后更新：2026-11-24（V0 基础搭建；尚无已完成版本）

本文是版本规划。**只有当前版本的范围在提案中确定**；后面的版本是计划，每完成一个版本按结果调整本文。

## 1. 推进方式

- **按后台能力模块逐个搭建**（模块见 `vision.md` 第 4 节）：一个阶段完成一个或两个模块，模块按依赖顺序排列，下游模块开工时上游已经可用、经过测试。
- **版本号 = 阶段.里程碑**：阶段号对应模块，里程碑是阶段内一个可验收的成果。版本的工作量不固定，可能需要一组或几组会话（一组 = 方案与学习会话 + 实施会话）。
- **先后端，后前端**：前端之前，用 API 文档页（FastAPI 自带的交互式文档）、命令行与生成的 HTML 报告验收；界面在第 10 阶段统一做。
- **每个模块自带测试与评测**：涉及 LLM 的模块在本模块内建评测集与评测页，不留到最后；第 10 阶段只做跨模块的整体评测与可观测性。
- **虚构数据集是一等交付物**：由用户依据业务经验编写，同时作为评测集与演示数据（V3.1）。
- 规模估计：约 30 个版本、35–45 组会话。各版本"可验收的里程碑"写在第 2 节，开工时在提案中细化。

## 3. 各阶段要点

每个阶段列出：主要知识主题（详见 `learning/README.md`）、开工时需要确定的问题、讨论稿中带入的设计要点。设计要点是候选，在该版本的提案中确认或推翻。

### 阶段 1 业务数据

- **知识**：Python 工程（虚拟环境、依赖管理、包结构、配置与密钥）、关系建模（实体、关系基数、主键与外键、约束、范式）、SQL、ORM 与迁移、数据库选型、测试；HTTP 与 REST、FastAPI、Pydantic、依赖注入、分层架构；事务与 ACID、隔离级别、丢失更新、乐观锁与悲观锁、审计。
- **待定**：
  - "一个项目"的业务定义；项目、合同、订单之间是一对一、一对多还是多对多（由用户依据业务经验确定）。
  - 第一版的实体清单：客户、项目、合同、订单、订单行、交付批次、付款节点、发票、付款、来源文件等。
  - 合同号、订单号是否全局唯一；系统内部主键与业务编号分开。
  - 数据库、ORM、迁移工具、包管理工具；Python 版本（若进程内调用 Minimal-RAG，需为 3.11）。
  - 审计记录的粒度（字段级 / 记录级）；哪些字段需要版本历史。
- **带入要点**：一个项目不等于一行记录；提取用的 Schema 与数据库 Schema 可以不同；金额用定点小数，币种单独存；保留原值与标准化值；成功变更的审计记录与业务更新在同一事务提交；审计（谁基于什么证据改了什么）、执行日志（程序跑了什么）、检查点（流程停在哪）是三种东西。

### 阶段 2 LLM 调用层

- **知识**：LLM API 基础（消息、token、温度、上下文窗口、流式输出）、推理基础（预填充与解码、KV Cache、提示缓存）、结构化输出的几种方式（提示词约定 JSON、JSON 模式、函数调用、约束解码）与失败处理、超时与重试（可重试 / 不可重试错误、指数退避、抖动）、熔断、降级、模型路由、限流算法（固定窗口、滑动窗口、令牌桶）与按用户计数、成本计量与归属、结果缓存。
- **待定**：LLM 提供方与模型（单一提供方 / 经 OpenRouter 等聚合）；限流计数放在进程内还是 Redis。
- **带入要点**：其余模块只通过本层调用 LLM；调用记录（输入版本、输出、token、成本、耗时、错误）是评测与审计的依据。

### 阶段 3 文档处理

- **知识**：提示词设计与版本管理、提取评测（字段级精确率、召回率、F1）、标注规范、依赖接入方式（库 / 服务）的取舍。
- **待定**：第一批文件类型与字段清单、必填性（由用户确定）；分类与提取的策略（一次调用同时分类与提取 / 先分类再用专属 Schema 提取 / 规则优先、拿不准再用 LLM，以第二种为可测基线）；Minimal-RAG 的接入方式。
- **带入要点**：不为填满 Schema 编造字段，区分"已提取、有问题、未找到、无法确定"；每个字段带来源（文件、页码或工作表、原文片段、位置）；文件哈希只能识别相同文件，不能识别同一业务项目；文件内容是不可信数据。

### 阶段 4 导入与变更管理

- **知识**：数据校验的层次、实体解析、规则与 LLM 的分工、差异比较；Workflow 与 Agent 的区别、状态机、检查点与恢复、人工审批模式、LangGraph（状态、节点、边、条件路由、中断）；幂等键与唯一约束、乐观并发在审批场景中的用法、故障注入测试。
- **待定**：同一项目、合同、订单的判定规则；重复上传、修订版、不同业务文件的区分；审批粒度（整个变更集 / 单个字段）；编排用 LangGraph 还是自写持久化在数据库中的状态机（提案中比较）。
- **带入要点**：导入新项目与补充已有项目共用流程，在目标识别、查重、更新策略上分支；先确认"是谁"，再判断"变了什么"；客户、金额、产品相似不能单独证明是同一项目；用户选"新建"不代表库里没有，选"补充"也要校验文件确实属于该项目；拟变更集只含真正要写入的变化，带旧值、新值、来源与警告；审批绑定变更集的具体版本，修改后旧批准失效；等待审批期间不持有数据库事务；审批与写入分开，恢复执行不重复产生副作用；版本冲突与唯一约束冲突不重试；拒绝等未写入的事件也要记录。

### 阶段 5 计划引擎

- **知识**：有向无环图与拓扑排序、依赖与层级两种关系、规则的表达方式（代码 / 配置 / 小型 DSL）、日期、工作日历与时区、增量重算。
- **待定**：第一批计划模板与日期规则（由用户依据业务确定）；AND / OR 前置条件的表达；生产周期参数的来源。
- **带入要点**：业务依赖图是项目数据，存数据库，不是 Workflow 图；事实入库成功不等于计划完整，缺条件时保存依赖与"待确定"并标注缺什么；合同约束、预测日期、实际日期、正式到期日分开；日期计算、硬约束、依赖判断用确定性代码，LLM 只从条款中识别参数，模糊条款交人工澄清；重算不是整体平移，内部延期不等于合同延期；FOB 下"交货""装船""提单日"按合同口径区分。

### 阶段 6 事件与后台任务

- **知识**：命令与事件、同步调用 / 数据库事件表 + Worker / 消息队列三种做法的取舍、Transactional Outbox、至少一次投递与幂等消费、定时任务（APScheduler、Celery Beat、系统 cron）、后台进程、重试与告警。
- **待定**：事件的实现层级（倾向数据库事件表）；提醒的状态与去重规则。
- **带入要点**：Outbox 降低"业务已更新、后续触发丢失"的风险，但不保证只处理一次；定时提醒不需要 LLM，也不是 Agent；调度更新后旧的已排程动作要失效。

### 阶段 7 Agent 运行时与知识检索

- **知识**：Agent 循环（ReAct）、函数调用、工具设计（粒度、描述、参数、错误返回、只读与写入）、工具过多时的选择与加载、权限校验放在哪一层、步数熔断与死循环检测、工具调用格式错误的容错；MCP（要解决的问题、Server 与 Client、工具 / 资源 / 提示、传输方式、错误类型）与函数调用、Skill 的区别；上下文工程（组装、预算、裁剪顺序、压缩与压缩失真的检测）、短期记忆；Agent 框架对比（LangGraph、OpenAI Agents SDK、Claude Agent SDK、PydanticAI）与 Agent Harness 的概念。
- **待定**：是否在手写循环之后改用框架；MCP 传输方式。
- **带入要点**：工具权限由后端执行，不靠提示词；工具返回的内容是不可信数据。

### 阶段 8 问答

- **知识**：查询路由、参数化查询工具与 Text-to-SQL 的取舍、结构化与非结构化来源的整合、引用、问答评测与错误归因。
- **带入要点**：金额、日期等事实以数据库查询结果为准，不用 RAG 或记忆回答；一个问题可能同时要查数据库和知识库。

### 阶段 9 跟进与协调

- **知识**：长任务编排（长生命周期流程与分段执行）、Skills（按需加载、与提示词和工具的区别、怎么判断一个 Skill 有效）、对外动作审批、提示注入（含间接注入）防护；规划与执行、检查器、路径震荡；多 Agent 模式（编排者-执行者、移交）、子 Agent 的上下文隔离、多 Agent 的通信与共享状态冲突、什么时候不该用多 Agent、A2A；长期记忆的提取、存储、取回与剪枝，Markdown 文件记忆与向量记忆的取舍。
- **待定**：跟进执行用分段执行 + 数据库状态衔接还是长生命周期流程（倾向前者）；模拟外部各方的方式。
- **带入要点**：跟进任务状态、业务任务状态、业务事实及核验状态分开；发送成功不等于业务完成，模糊回复保留不确定性与来源；同一联系人的跟进频率上限、工作时间与时区；销售运营 Agent 没有生产、财务、物流的决策权，不虚构其他部门的承诺，不绕过"款到放货"；Agent 可以提议再规划，计算与约束检查由计划引擎完成，高风险修改经审批。

### 阶段 10 整体评测、可观测性、前端与部署

- **知识**：Tracing（Langfuse、LangSmith、OpenTelemetry）、按会话与用户的成本归属、Agent 评测（任务成功率、轨迹评测、LLM 评判及其偏差、线上日志转评测集）、前后端分离与跨域、前端技术选型（Streamlit / Gradio 与 React）、Docker 与 Docker Compose、云服务器与进程守护。
- **待定**：前端技术；部署平台。

## 4. 暂不纳入

多文件批量导入与跨文档自动整合、完整历史修订链、无人审批的自动写库、多用户与角色权限、真实外部系统（邮箱、ERP、财务）接入、跨项目产能优化。需要时在本节写明重新启动的条件，再移入版本规划。
